1. PROJECT OVERVIEW
================================================================================

Project Name     : Legal Metrology Verification Portal
Hackathon        : Smart India Hackathon 2026
Problem ID       : SIH26036
Category         : Government / Regulatory Technology

This is a full-stack web application that digitizes the statutory verification
process for commercial weighing and measuring instruments in India. Under the
Legal Metrology Act, 2009 (Section 24), all commercial instruments such as
weighing scales, capacity measures, length tapes, beam scales, counter machines,
and tank lorries must be periodically verified and stamped by authorized
Government officers.

This portal replaces the manual, paper-based verification system with a digital
workflow covering:
  - Online application submission by businesses
  - Automatic allocation of applications to jurisdiction officers
  - Digital inspection review and certificate issuance
  - QR-code-based public certificate verification
  - GIS-based mapping of applications and officer locations
  - Administrative oversight with workload monitoring and heatmaps


================================================================================
2. PROBLEM STATEMENT & REAL-WORLD CONTEXT
================================================================================

Under current practice in India:
  - Businesses physically visit the Legal Metrology Department to submit forms
  - Officers manually inspect instruments and issue handwritten certificates
  - Certificates are paper-based and easily forged
  - There is no centralized tracking of instrument verification status
  - Consumers have no way to verify if a shop's weighing scale is legally certified

This portal solves all of these problems by providing:
  1. An online submission portal for businesses
  2. A digital review workflow for officers
  3. Tamper-proof digital certificates with QR codes
  4. A public verification page for consumers and field inspectors
  5. Automatic statutory expiry tracking (12 or 24 months per instrument type)
  6. GIS integration for location-based assignment and routing

Legal Reference:
  - Legal Metrology Act, 2009 (Sections 24, 33)
  - Legal Metrology (General) Rules, 2011 (Rule 24)
  - Penalty for unverified instruments: Rs. 2,000 to Rs. 10,000 (Section 33)

6. FIREBASE COLLECTIONS (Database Schema)
================================================================================

Collection: "users"
  - Document ID: Firebase Auth UID
  - Fields: email, name, role ('business' | 'officer' | 'admin'), createdAt

Collection: "applications"
  - Document ID: Auto-generated
  - Fields: All fields from the Application interface above
  - Created when a business submits a new verification request
  - Updated when an officer approves/rejects/adds remarks

Collection: "officerRegistrations"
  - Document ID: Firebase Auth UID
  - Fields: All fields from the OfficerRegistration interface
  - Created when an officer submits their registration form
  - Updated when an admin approves or rejects the registration

Collection: "officers"
  - Document ID: Firebase Auth UID
  - Fields: All fields from the Officer interface
  - Created automatically when admin approves an officer registration
  - Updated when allocation assigns workload

Collection: "auditLogs"
  - Document ID: Auto-generated
  - Fields: action, performedBy, targetId, previousValue, newValue,
            metadata (object), timestamp
  - Created on every critical action (submit, approve, reject, assign, etc.)

Storage Bucket: "officer-id-cards/"
  - Stores uploaded officer identification card images
  - Files named by UID for uniqueness
  - Access restricted (not publicly accessible)

7. USER ROLES & ACCESS CONTROL
================================================================================

Role              | Description                         | Access Level
------------------+-------------------------------------+----------------------------
business          | Commercial establishment owner       | Submit apps, view certs
officer           | Verified Legal Metrology Inspector   | Review apps, issue certs
pending_officer   | Officer awaiting admin approval      | No access (waiting)
admin             | System administrator                 | Verify officers, dashboard
null (public)     | Unauthenticated visitor              | Verify certificates only

Role Assignment Rules:
  - Users who sign up via the Business card get role = 'business'
  - Users who sign up via the Officer card get role = 'officer' BUT must
    complete OfficerSignup page and await admin approval
  - Admin role is set manually in Firestore (cannot be self-assigned)
  - Login enforces role-portal matching: a business user CANNOT log in
    through the officer portal and vice versa (throws "Access Denied")

8. AUTHENTICATION FLOW
================================================================================

Sign Up (Business):
  1. User fills in email + password on the Business card (LandingPage)
  2. Firebase Auth creates user account
  3. Firestore "users" document created with role = 'business'
  4. User is redirected to /business (BusinessDashboard)

Sign Up (Officer):
  1. User clicks "Register as Officer" link
  2. Redirected to /officer-signup (OfficerSignup page)
  3. Fills detailed form: name, officer ID, department, designation,
     district, state, and uploads ID card image
  4. Firebase Auth creates user, Storage stores ID card image
  5. Firestore "users" doc: role = 'officer', "officerRegistrations" doc created
  6. User must wait for admin to approve before accessing the system

Login:
  1. User enters email + password on either card (LandingPage)
  2. System authenticates with Firebase Auth
  3. System fetches actual role from Firestore "users" document
  4. STRICT VALIDATION: If actual role does not match the portal used for
     login, the system immediately logs them out and shows an error:
     "Access Denied: This email is registered as a [role]. Please use the
     correct login portal."
  5. On success, user is redirected to their role-appropriate dashboard

Logout:
  - Available from Navbar for all authenticated users
  - Clears Firebase Auth session and React state
  - Redirects to Landing Page

9. CORE WORKFLOWS
================================================================================

9.1 BUSINESS USER WORKFLOW
--------------------------
  1. Login/Signup via Business card on Landing Page
  2. View BusinessDashboard showing all submitted applications with:
     - Status badges (Pending / Approved / Rejected)
     - Search and filter functionality
     - Summary stat cards (pending count, approved count, rejected count)
  3. Click "New Application" to go to ApplyPage
  4. Fill the instrument verification form:
     - Instrument name, type (from statutory categories), serial number
     - Owner name, contact number
     - Address, district, state
     - Pin exact GPS location on interactive Leaflet map
  5. Form validation enforces real data (readable text checks, valid phone,
     valid serial number, location pin required)
  6. On submit:
     - Application stored in Firestore with status = 'Pending'
     - Auto-allocation runs to assign the nearest/least-busy officer
     - Success confirmation page displayed with Application ID and status
  7. Once approved, click "View Certificate" to see digital certificate
  8. Download certificate as PDF with embedded QR code

9.2 OFFICER WORKFLOW
--------------------
  1. Complete officer registration (OfficerSignup) with ID card upload
  2. Wait for admin approval
  3. Once approved, login and see OfficerDashboard:
     - "My Queue" tab: Assigned applications with review buttons
     - Interactive GIS map showing all assigned application locations
     - "Plan Route" button to compute optimal inspection route
  4. Click "Review" on any application to go to ReviewPage:
     - View all instrument details, owner info, location on map
     - Record inspection findings (remarks)
     - Choose "Approve" (generates certificate) or "Reject" (with reason)
  5. On approval:
     - Certificate ID is generated (format: LM-CERT-XXXXXX)
     - Issue date = today, expiry date = today + reverification months
     - Application status updated to 'Approved'
     - Audit log recorded
     - Toast notification confirms success
  6. Route Planning:
     - Uses nearest-neighbor algorithm to plan optimal inspection order
     - Draws a blue dashed polyline on the map connecting locations

9.3 ADMIN WORKFLOW
------------------
  1. Login (admin role is assigned manually in Firestore)
  2. Navigate to /admin/officer-verification (AdminDashboard)
  3. Three tabs available:

     Tab 1: VERIFICATION QUEUE
     - Lists all pending officer registrations
     - Shows name, officer ID, department, district, submission date
     - View uploaded ID card image
     - Approve or Reject each registration
     - On approve: creates "officers" collection entry, updates user role
     - On reject: records reason, marks registration as rejected

     Tab 2: OFFICER WORKLOAD
     - Table of all approved officers
     - Columns: Name, Officer ID, District, Availability, Workload count
     - Used for monitoring load distribution

     Tab 3: APPLICATION HEATMAP
     - Interactive Leaflet map showing all applications as markers
     - Markers color-coded by status (Pending/Approved/Rejected)
     - Useful for identifying high-density areas

9.4 PUBLIC VERIFICATION WORKFLOW
---------------------------------
  1. Navigate to /verify (no login required)
  2. Enter a Certificate ID (format: LM-CERT-XXXXXX)
  3. System looks up the certificate in Firestore
  4. Displays:
     - Certificate validity status (VALID / EXPIRED)
     - Instrument details (name, type, serial number)
     - Owner and premises information
     - Issue date and expiry date
     - Verifying officer name
     - QR code for sharing
  5. Also accessible by scanning QR code on physical/digital certificate

Component: src/components/GISMap.tsx

The GISMap is a reusable React component wrapping react-leaflet. It supports:

  Props:
    - center     : [lat, lng] — map center coordinates
    - zoom       : number — initial zoom level
    - markers    : Array of { position, popupText, color? }
    - selectable : boolean — if true, clicking the map pins a location
    - onSelect   : callback returning (lat, lng) when user clicks map

  Used in:
    - ApplyPage: selectable=true for pinning instrument location
    - OfficerDashboard: markers for assigned applications + route polyline
    - OfficerVerificationPage (Admin Heatmap): markers for all applications

  Map tiles are loaded from OpenStreetMap (free, no API key needed).

12. AUTOMATIC OFFICER ALLOCATION ALGORITHM
================================================================================

File: src/firebase/allocation.ts
Function: autoAllocateApplication(appId, district, category, appLat, appLng)

Algorithm Steps:

  1. QUERY eligible officers from Firestore:
     - Same district as the application
     - verificationStatus = 'approved'
     - available = true

  2. FILTER by instrument category support
     (simplified for MVP: all approved officers can handle all categories)

  3. SORT by two criteria:
     a. PRIMARY: Lowest workload first (officer with fewest active cases)
     b. TIE-BREAKER: If two officers have equal workload, use Turf.js to
        calculate geographic distance from each officer's location to the
        application's location. Closer officer wins.

  4. ASSIGN using Firestore WriteBatch (atomic operation):
     - Update application: assignedOfficerId, assignedOfficerName, assignedAt
     - Update officer: workload += 1

  5. AUDIT: Record an 'officer_assigned' audit log entry

  If no eligible officer is found, application gets assignmentStatus = 'unassigned'.

  NOTE: In production, this logic should be moved to a Firebase Cloud Function
  for security and atomicity guarantees.

13. AUDIT LOGGING SYSTEM
================================================================================

File: src/firebase/audit.ts

Every critical action in the system is logged to the "auditLogs" Firestore
collection for accountability and compliance tracking.

Tracked Actions (AuditAction type):
  - application_submitted
  - officer_registration_submitted
  - officer_registration_approved
  - officer_registration_rejected
  - officer_assigned
  - officer_reassigned
  - inspection_recorded
  - application_approved
  - application_rejected
  - certificate_issued
  - certificate_revoked

Each Log Entry Contains:
  - action     : The action type
  - performedBy: UID of the user who performed the action (or 'system')
  - targetId   : The document ID affected
  - previousValue / newValue: Before/after state
  - metadata   : Additional context (officer name, district, etc.)
  - timestamp  : ISO date string

Audit logging is non-blocking: if the log write fails, it does not break
the main operation (logged to console instead).

15. SECURITY MEASURES
================================================================================

  1. ROLE ENFORCEMENT: Each portal card enforces strict role matching.
     Logging in with a business email on the officer card shows "Access Denied"
     and immediately logs the user out.

  2. NO SELF-ROLE ESCALATION: Users cannot assign themselves 'admin' or
     'officer' roles. Officer role requires registration + admin approval.
     Admin role is only set directly in Firestore by a system administrator.

  3. OFFICER ID CARD PRIVACY: Uploaded officer ID card images are stored in
     Firebase Storage and only viewable by admins during verification.

  4. ROUTE GUARDS: Dashboard pages check the user's role before rendering.
     Unauthorized access redirects to the landing page.

  5. FIRESTORE RULES: Should be configured to restrict read/write access
     based on authenticated user's role (configured in Firebase Console).

  6. AUDIT TRAIL: Every critical action is logged with the performer's UID,
     timestamp, and details, creating an immutable compliance record.

  7. INPUT VALIDATION: ApplyPage enforces readable text checks, phone number
     validation, and serial number minimum length to prevent garbage data.

  8. ATOMIC WRITES: Officer allocation uses Firestore WriteBatch to ensure
     the application assignment and officer workload update happen atomically.

  2. Install dependencies:

  3. Configure Firebase:
     - Create a Firebase project at https://console.firebase.google.com
     - Enable Email/Password authentication
     - Create a Firestore database
     - Enable Firebase Storage
     - Copy your Firebase config to src/firebase/config.js

  4. Start the development server:
     > npm run dev

  5. Open in browser:
     > http://localhost:3000

  6. Create an admin user:
     - Sign up as a regular user
     - Go to Firebase Console → Firestore → "users" collection
     - Find your user document and change role from 'business' to 'admin'

  7. Build for production:
     > npm run build
     (Output goes to /dist folder)
